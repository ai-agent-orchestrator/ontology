# 선택형 Legal Intake와 미니 법률 온톨로지

## 핵심 문장

```text
고객은 선택하고, 챗봇은 정리한다.
```

이 문서는 법률 상담 전환 손실 문제를 `선택형 Legal Intake Form`과 `미니 법률 온톨로지`로 구조화하는 설계 초안입니다.

목표는 완성형 법률 상담 챗봇이 아닙니다.
고객이 법률 용어를 몰라도 자신의 상황을 선택형으로 입력하고,
챗봇이 이를 현재 사건 유형, 분쟁 영역, 준비 자료, 다음 정리 방향으로 바꾸는 intake 구조를 설계하는 것입니다.

## 문제 정의

많은 서비스는 키오스크나 선택형 UI를 통해 고객의 입력 부담을 줄이고 있습니다.
그러나 법률 상담의 초기 응대는 여전히 고객에게 자신의 문제를 처음부터 주관식으로 설명하도록 요구하는 경우가 많습니다.

법률 문제를 처음 겪는 고객은 자신의 문제가 민사인지, 형사인지, 가사인지조차 알기 어렵습니다.
그런 상태에서 전화로 사건을 논리적으로 설명하라고 요구하면, 날짜, 금액, 상대방, 보유 자료, 원하는 도움 같은 핵심 정보가 빠지기 쉽습니다.

반대로 소규모 법률 사무소의 초기 응대는 담당자의 법률 이해도와 경험에 크게 의존하는 경우가 많습니다.
고객과 변호사 사이에서 필요한 정보가 구조화되지 못하면 상담 전환 흐름이 끊기고, 변호사도 정리되지 않은 상담에 많은 시간을 쓰게 됩니다.

따라서 Legal Intake는 단순 전화 응대가 아니라,
고객이 필요한 정보를 빠뜨리지 않도록 돕는 템플릿형 입력 구조가 필요합니다.

## 기존 흐름과 개선 흐름

기존 전화 중심 intake는 고객에게 주관식 설명을 요구합니다.

```text
무슨 일인지 자세히 설명해 보세요.
-> 고객은 법률 용어를 모름
-> 감정과 사실이 섞임
-> 날짜, 금액, 증거가 빠짐
-> 데스크에서 구조화하지 못함
-> 변호사에게 전달되는 정보 품질이 낮아짐
```

개선된 선택형 intake는 고객이 고르고, 시스템이 정리합니다.

```text
고객:
객관식 / 체크박스 / 짧은 서술형으로 선택

챗봇:
선택된 내용을 사건 구조로 정리

출력:
현재 사건 유형
분쟁 영역
준비 자료
다음 정리 방향
개인정보 마스킹 안내
```

## Minimal Legal Intake Form

이번 설계의 핵심 입력 구조는 아래 6개 항목입니다.

### 1. 문의 목적

- 절차 안내
- 필요한 자료 확인
- 작성한 문서 검토
- 변호사 선임/계약 검토
- 전자소송 제출 안내

### 2. 사건 유형

- 민사
- 형사
- 가사
- 전자소송
- 잘 모르겠음

### 3. 당사자 위치

- 피해자
- 피고소인
- 원고
- 피고
- 신청인
- 상대방
- 잘 모르겠음

### 4. 핵심 사실

- 사건 발생일
- 상대방
- 문제가 된 금액 또는 피해 규모
- 현재 진행 단계
- 핵심 내용 한 문장

### 5. 보유 자료

- 계약서
- 입금 내역
- 카카오톡/문자
- 사진/영상
- 소장/고소장/통지서
- 없음

### 6. 원하는 다음 단계

- 상담
- 서면 검토
- 소송 준비
- 전자소송 제출
- 변호사 선임

## 미니 법률 온톨로지

이 설계에서 온톨로지는 복잡한 법률 지식 그래프가 아닙니다.
고객의 선택값과 키워드를 사건 유형, 분쟁 영역, 준비 자료로 연결하는 최소 분류 체계입니다.

```text
고객 입력
-> 선택값
-> 사건 유형
-> 분쟁 영역
-> 준비 자료
-> 다음 정리 방향
```

예시 구조:

```text
민사
-> 대여금
-> 계약금
-> 임대차
-> 손해배상

형사
-> 사기
-> 폭행
-> 고소
-> 피고소

가사
-> 이혼
-> 양육비
-> 상속
-> 친권

전자소송
-> 소장
-> 답변서
-> 보정명령
-> 송달
```

## 입력과 출력 예시

입력:

```text
문의 목적: 필요한 자료 확인
사건 유형: 민사
당사자 위치: 원고
보유 자료: 입금내역, 카카오톡
원하는 다음 단계: 상담
핵심 내용: 빌려준 돈을 못 받고 있습니다.
```

출력:

```text
현재 문의는 민사 사건에 가까워 보입니다.

금전 반환 또는 대여금 분쟁 가능성이 있습니다.
상담 전에는 입금 내역, 카카오톡/문자 대화,
상대방에게 반환을 요청한 기록을 날짜순으로 정리해 주세요.

계약서나 약정서가 있다면 함께 준비하는 것이 좋습니다.
입력하신 개인정보는 답변에 그대로 표시하지 않고 마스킹 처리됩니다.
```

고객은 이 출력만으로도 다음을 이해할 수 있습니다.

```text
아, 내 사건은 민사 쪽이구나.
금전 반환 문제로 볼 수 있구나.
입금내역과 카카오톡을 날짜순으로 정리하면 되는구나.
계약서가 있으면 더 좋구나.
이 사무실은 체계적이고 친절하구나.
```

## 제품 가치

### 1. 고객 가치

고객은 법률 용어를 몰라도 선택형 입력을 통해 자신의 문제를 정리할 수 있습니다.

- 내 문제가 민사, 형사, 가사, 전자소송 중 어디에 가까운지 감을 잡을 수 있습니다.
- 상담 전에 어떤 자료를 준비해야 하는지 알 수 있습니다.
- 전화하기 전에 불안이 줄어듭니다.
- 사무소가 체계적으로 응대하고 있다는 인상을 받습니다.
- 상담료를 내더라도 왜 필요한지 이해하기 쉬워집니다.

### 2. 변호사 가치

변호사는 상담 전에 고객 문의를 구조화된 형태로 확인할 수 있습니다.

- 상담 전 사건 방향을 빠르게 파악할 수 있습니다.
- 고객의 자료 정리 상태가 개선됩니다.
- 기본 질문을 반복하는 시간이 줄어듭니다.
- 고객 전환율을 개선할 수 있습니다.
- 변호사가 사무실에 계속 상주하지 않아도 초기 문의 흐름을 관리할 수 있습니다.
- 광고 유입 고객을 놓치지 않고 상담 가능 상태로 구조화하는 저비용 고효율 마케팅 도구로 활용할 수 있습니다.
- 상담 만족도가 올라가면 상담 후 계약 전환율도 높아질 수 있습니다.

### 3. 시스템 가치

시스템은 긴 자유입력과 불필요한 LLM 호출을 줄일 수 있습니다.

- 선택형 입력으로 자유입력 길이를 줄입니다.
- 사건 유형별 템플릿 응답을 활용할 수 있습니다.
- DTO Validation과 reasonCode 설계가 쉬워집니다.
- Cost Control을 적용하기 쉬워집니다.
- 개인정보 출력 마스킹, 보안 guardrail, metric 수집을 안정적으로 붙일 수 있습니다.

## 비용 절감 구조

선택형 intake와 미니 법률 온톨로지는 고객, 변호사, 시스템 모두의 비용을 줄이는 구조입니다.

- 고객은 법률 용어를 몰라도 선택할 수 있어 입력 부담이 줄어듭니다.
- 변호사는 상담 전에 사건 유형과 보유 자료를 파악할 수 있어 기본 질문 시간이 줄어듭니다.
- 시스템은 긴 자유입력을 줄이고 템플릿 기반 응답을 활용할 수 있어 LLM 비용을 줄일 수 있습니다.

이 구조의 핵심은 법률 판단을 과장하는 것이 아니라,
상담 전에 고객과 변호사가 서로 필요한 최소 정보를 같은 구조로 바라보게 만드는 것입니다.

```text
고객은 덜 헤맨다.
변호사는 덜 묻는다.
시스템은 덜 호출한다.
```

## Marketing / Operation 관점

좋은 마케팅은 과장 광고가 아니라, 고객이 막힌 순간에 다음 행동을 알려주는 것입니다.

```text
현재 문의는 민사 사건에 가까워 보입니다.
금전 반환 분쟁 가능성이 있습니다.
입금 내역과 카카오톡 대화를 날짜순으로 정리해 주세요.
```

이 정도 안내만으로도 고객은 다음을 느낄 수 있습니다.

```text
내 말을 어느 정도 이해하고 있구나.
뭘 준비해야 하는지 알겠다.
이 사무실은 체계가 있구나.
```

개인사업자인 변호사 입장에서는 이 intake 흐름이 저비용 고효율 마케팅 채널이 될 수 있습니다.
광고비를 더 쓰기보다, 이미 들어온 문의를 놓치지 않게 만드는 자동 intake 마케팅 시스템으로 볼 수 있습니다.

## 보안형 AI Intake로의 연결

선택형 intake는 보안 구조와도 잘 맞습니다.

```text
구조화된 입력
-> DTO Validation 쉬움
-> Fixed Guard 적용 쉬움
-> Cost Control 적용 쉬움
-> Privacy Output Guard 적용 쉬움
-> Prometheus metric 수집 쉬움
```

법률 intake에서는 개인정보 입력 자체를 무조건 막을 수 없습니다.
대신 출력에서 개인정보를 마스킹하고, 위험 요청과 비용 폭주를 LLM 호출 전에 통제해야 합니다.

```text
Fixed Guard
-> 위험 요청 차단

Dynamic Guard
-> 반복 위험 행동 차단

Cost Control
-> 긴 입력과 토큰 비용 폭주 차단

Privacy Output Guard
-> 개인정보 출력 마스킹
```
